# Build a client

Design your application around bxapi's client-scoped keys, server-driven game loop, and concurrency controls. For exact request bodies, query parameters, response schemas, and per-endpoint error codes, refer to the [API reference](https://mmacy.github.io/bxapi/reference/).

## Choose a key and client topology

bxapi has no user accounts. Each API key identifies a client application (`client`) and grants either the `player` or `referee` role (see [Authentication](https://mmacy.github.io/bxapi/reference/#authentication)):

- Every key configured with the same `client` name shares that client's characters, adventures, sessions, saves, storage quota, and per-process rate limit, regardless of role.
- To rotate a secret without invalidating active clients, add a second key entry for the same `client` in `BXAPI_API_KEYS` (restarting each `bxapi` process to load the updated setting), roll the new key out to your application, and then remove the old entry.
- A request for a resource owned by another `client` receives the same 404 `not_found` response as a request for an unknown ID.

Match your client topology to your trust boundary:

1. **Backend proxy (required to isolate untrusted users):** Run a backend service that stores the bxapi key, authenticates your users, maps `chr_`, `adv_`, `ses_`, and `sav_` IDs to user accounts in its database, filters list responses, and verifies ownership on IDs in both URL paths and request bodies (such as `character_ids` on [`POST /v1/sessions`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-create_session)). Players never see the bxapi key.
2. **Direct browser or native client (single-user tools or shared-trust groups):** Embed a `player` key in the client (browser apps also require `BXAPI_CORS_ORIGINS`, covered in [Configure and deploy](configuration.md#allow-browser-origins)), or configure a distinct `client` entry per user group. Random 22-character IDs prevent casual guessing, but CORS does not restrict key holders: anyone who extracts a shared `player` key from client traffic can list and modify every resource under that `client` name via endpoints such as [`GET /v1/sessions`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-list_sessions).

Keep `referee` keys on trusted servers, administrative tools, or test harnesses. Never embed a `referee` key in browser or mobile code, where a player could read hidden state or issue referee commands across your client's sessions. Call [`GET /v1/meta`](https://mmacy.github.io/bxapi/reference/endpoint/meta#operation-get_meta) when your application starts to verify your key, check `role` and `schema_version`, and inspect `storage.used_bytes` against `storage.max_bytes`.

## Drive the UI from catalogs, command schemas, and views

An active session follows a three-step loop until `ended` is `true`:

1. Read [`GET /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-list_session_commands) to list the commands legal in the current `mode` for your key's role, along with the current `revision`.
2. Send the chosen move to [`POST /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-send_command) with `include=view` so the response returns `accepted`, `rejections`, `events`, `messages`, the new `revision`, and the updated player view (`view`) in one round-trip.
3. Render `messages` (or `rejections` when `accepted` is `false`) and redraw your interface from `view`.

Keep rules logic out of your client by reading catalog data, schemas, and player-visible state from the server:

- **Rules catalogs:** Populate class pickers, spellbooks, equipment shops, and bestiaries from the [`/v1/rules/*` endpoints](https://mmacy.github.io/bxapi/reference/endpoint/rules). Every 200 response under `/v1/rules` includes `Cache-Control: private, max-age=3600` and an `ETag`, so your client can cache catalog pages locally and revalidate them with `If-None-Match`. Catalog endpoints return complete rulebook entries to both roles, including details hidden during play (such as whether a magic item in [`GET /v1/rules/magic-items/{item_id}`](https://mmacy.github.io/bxapi/reference/endpoint/rules#operation-get_magic_item) is cursed).
- **Masked items and monster groups in the player view:** In the player view ([`GET /v1/sessions/{session_id}/view`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_player_view)), osrlib masks unidentified magic item names in a party member's `inventory`, whereas combat numbers such as `armour_class` and `thac0` already include every equipped item's bonus or penalty because combat rolls use those numbers. In `encounter.groups`, identify creature types programmatically from `family_id` and `categories` (such as `undead`) rather than matching on display `label` strings. A `family_id` can span multiple monster templates (for example, `hellhound_3` through `hellhound_7`), and passing `family_id` as `q` to [`GET /v1/rules/monsters`](https://mmacy.github.io/bxapi/reference/endpoint/rules#operation-list_monsters) performs a substring match (`goblin` also returns `hobgoblin`). When an encounter has multiple monster groups, only [`GET /v1/sessions/{session_id}/referee-view`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_referee_view) maps individual `monster-NNNN` IDs from combat messages to each group's `monster_ids`.
- **Dynamic command forms:** Generate typed command payloads from `/openapi.json`, or build forms dynamically at run time from the `json_schema` returned by [`GET /v1/rules/commands/{command_type}`](https://mmacy.github.io/bxapi/reference/endpoint/rules#operation-get_command). Always include `command_type` in HTTP command bodies (even though osrlib's raw Pydantic schema lists `command_type` with a default rather than inside `required`), and omit `source` when calling with a `player` key.
- **Hit points and gold before creation:** Call [`POST /v1/ability-rolls/{roll_id}/preview`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-preview_character) with the player's choices to get the character, its derived stats, and its hit point and gold rolls that [`POST /v1/characters`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-create_character) would create from a stored ability roll. The preview stores nothing and leaves the roll unused. For one roll, the hit point and gold rolls change only with `class_id` and `hp_reroll_at_first_level`, so you can show the gold once the player picks a class and preview again to check the purchases.
- **Stateless rolls and previews:** Use [`POST /v1/dice/roll`](https://mmacy.github.io/bxapi/reference/endpoint/dice#operation-roll_dice) and the [`/v1/generate/*` endpoints](https://mmacy.github.io/bxapi/reference/endpoint/generate) to roll dice, treasure hoards, monsters, stocked rooms, NPC parties, or character previews without storing database records. Any caller may pass an optional `seed` (`0` to `2^53 - 1`), and each response returns the `seed` used so your client can replay the exact result later.

## Handle refusals, retries, and concurrent clients

Separate normal gameplay refusals from transport and state-conflict errors (see [Refused commands](https://mmacy.github.io/bxapi/reference/#refused-commands) and [Errors](https://mmacy.github.io/bxapi/reference/#errors)):

- **Rule refusals vs. HTTP errors:** When B/X rules forbid a session command (such as stepping into a wall or attacking from the back rank), [`POST /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-send_command) returns `200 OK` with `accepted` set to `false`, osrlib's `rejections`, and `revision` unchanged. Character creation ([`POST /v1/characters`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-create_character), [`POST /v1/ability-rolls/{roll_id}/preview`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-preview_character), and [`POST /v1/generate/character`](https://mmacy.github.io/bxapi/reference/endpoint/generate#operation-generate_character)) is the sole exception: invalid choices return 422 `character_invalid`, with either osrlib's `rejections` (for rule violations such as overspending gold) or `field` and `id` (plus `index` on list fields) when a `class_id`, `item_id`, or unpurchased `equip_item_ids` entry doesn't exist. A 422 `character_invalid` error leaves `ability_roll_id` unused so the player can adjust choices and retry, whereas 409 `ability_roll_used` means a character was already created from that roll (deleting a character doesn't free its ability roll).
- **Problem documents and request tracing:** Every `4xx` or `5xx` error returns an `application/problem+json` body. Branch on the stable `code` field rather than `detail`, ignore unfamiliar fields, and log `request_id`. Send an `X-Request-Id` header (`1` to `128` characters from `A-Z`, `a-z`, `0-9`, `.`, `_`, `~`, and `-`) when you want to correlate requests across your services and bxapi's access log.
- **Safe `POST` retries with `Idempotency-Key`:** Send a fresh `Idempotency-Key` (such as a UUID) on every `POST` under `/v1`, and resend the identical request (same method, path, query string, role, and raw JSON body bytes) with that key whenever you retry a dropped connection or a transient error (`408 request_timeout`, `409 idempotency_key_in_progress`, `429 rate_limited`, or `503 database_busy`, waiting the seconds in `Retry-After` when present). Sending different serialized bytes under the same key returns 422 `idempotency_key_reused`. The server caches 2xx responses per client for 24 hours and replays them with `Idempotent-Replayed: true`. When the initial request fails with a problem other than 500 `internal_error`, nothing changed and the server releases the key (whereas a concurrent duplicate that receives 409 `idempotency_key_in_progress` leaves the in-flight claim active). If a retry returns 409 `idempotency_key_interrupted`, the server failed, stopped, or spent 60 seconds or more handling the first attempt and has no stored outcome: inspect the target session or resource list to verify whether the change took effect before sending a new request with a fresh key (on an overloaded server, recheck state first because the original attempt might still finish).
- **Concurrent session writers with `expected_revision`:** Whenever multiple players, browser tabs, or worker processes can send commands to the same session, pass the last known `revision` as the `expected_revision` query parameter on [`POST /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-send_command):
  - On 409 `revision_conflict`, another command already advanced the session (or your earlier attempt succeeded before its response was lost). Take the current `revision` from the `409` problem document (or from [`GET /v1/sessions/{session_id}`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_session) or [`GET /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-list_session_commands), because standalone `PlayerView` and `/events` omit `revision`), refresh [`GET /v1/sessions/{session_id}/view`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_player_view), decide whether the move still applies, and submit any follow-up command with that `revision`.
  - On 409 `session_busy`, the server didn't apply the command because another request locked the session for more than 5 seconds or another server process committed a write first. If you sent `expected_revision`, check [`GET /v1/sessions/{session_id}`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_session) before retrying so you notice if the revision changed. If you omitted `expected_revision`, retry directly (or combine `expected_revision` with `Idempotency-Key` so lost responses replay cleanly).
- **Polling and reconnects:** Send the previous response's `ETag` in `If-None-Match` when polling [`GET /v1/sessions/{session_id}`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_session) or [`GET /v1/sessions/{session_id}/view`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_player_view) so unchanged state returns `304 Not Modified` with an empty body. To catch up on missed messages after a disconnect, store `next_after` from [`GET /v1/sessions/{session_id}/events`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-list_events) (an event-log cursor scoped to `visibility` that advances independently of `revision`) and pass it as `after` on reconnect until `next_after` reaches `total`.

## Author and upload custom adventures

Every server includes `builtin-barrow`, and any authenticated caller (`player` or `referee`) can validate, upload, list, and delete custom adventures via the [Adventures endpoints](https://mmacy.github.io/bxapi/reference/endpoint/adventures).

Instead of writing adventure JSON by hand, generate an adventure document with [osr-forge](https://github.com/mmacy/osr-forge) (which converts adventure module PDFs), [osr-editor](https://github.com/mmacy/osr-editor) (a graphical adventure editor), or [osrlib](https://mmacy.github.io/osrlib-python/). An adventure can bundle custom spells in `spells`, override temple service prices in `town.healing_prices`, and bundle custom monster templates. If a bundled monster omits `family_id`, osrlib defaults `family_id` to the monster's template `id`, which the player view exposes in `encounter.groups`. Set `family_id` explicitly whenever a monster's template `id` would reveal a disguise or hidden identity to players.

1. Run [`POST /v1/adventures/validate`](https://mmacy.github.io/bxapi/reference/endpoint/adventures#operation-validate_adventure) in your editor or CI pipeline to check schema compatibility, cross-references (monsters, items, areas, and quests), and map constraints without storing anything:

   ```sh
   curl -sS -X POST http://127.0.0.1:8640/v1/adventures/validate -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" --data-binary @adventure.json
   ```

   Because `/v1/adventures/validate` returns HTTP `200` for both valid and invalid adventure documents, check that `valid` is `true` in the response body (not HTTP status alone) before gating a CI build.

2. Upload the validated document with [`POST /v1/adventures`](https://mmacy.github.io/bxapi/reference/endpoint/adventures#operation-upload_adventure) (`--data-binary @adventure.json`, up to `BXAPI_MAX_BODY_BYTES`, 8 MiB by default) and pass the returned `adv_` ID as `adventure_id` to [`POST /v1/sessions`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-create_session).

Each session embeds a copy of its adventure when created, so deleting an uploaded adventure with [`DELETE /v1/adventures/{adventure_id}`](https://mmacy.github.io/bxapi/reference/endpoint/adventures#operation-delete_adventure) leaves running sessions and saves unaffected. If a later osrlib upgrade introduces stricter adventure checks that an older stored adventure fails, starting a new session from that adventure returns 422 `content_invalid` until you upload a fixed document.

## Use referee features for backends, tools, and tests

A key with the `referee` role unlocks deterministic seeding, full game-state inspection, live referee intervention, and document portability across servers:

- **Deterministic sessions and rolls:** Pass `seed` (`0` to `2^53 - 1`) to [`POST /v1/ability-rolls`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-create_ability_roll), [`POST /v1/characters`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-create_character), or [`POST /v1/sessions`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-create_session). Two sessions started on the same osrlib version with the same `seed`, adventure, party, and command sequence produce identical dice rolls, which is useful for integration tests and bug reproduction.
- **Hidden state and referee events:** Call [`GET /v1/sessions/{session_id}/referee-view`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-get_referee_view) to inspect monster hit points, per-group `monster_ids`, the unexplored dungeon map, treasure caches, active effects, flags, and the full command and event logs (everything except the master seed and internal RNG state). Pass `visibility=referee` on [`POST /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-send_command) or [`GET /v1/sessions/{session_id}/events`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-list_events) to include referee-only events such as surprise, reaction, and treasure-hoard rolls alongside player events.
- **Referee commands and audit sources:** Send referee commands (`kind` set to `"referee"` in [`GET /v1/rules/commands`](https://mmacy.github.io/bxapi/reference/endpoint/rules#operation-list_commands), such as `grant_item`, `grant_coins`, `award_xp`, `spawn_monsters`, `place_party`, or `end_encounter`) to [`POST /v1/sessions/{session_id}/commands`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-send_command) to modify an active session directly. Referees may also set a command's optional `source` string, which osrlib records in `command_log` without changing rules execution.
- **Document import and export:** Move characters, parties, adventures, and saved games between bxapi servers or offline osrlib tools using osrlib's versioned JSON documents (`kind`, `schema_version`, `engine_version`, and `payload`):
  - Pass `party_document` (written by osrlib's `party_to_document`, up to 20 characters) instead of `character_ids` on [`POST /v1/sessions`](https://mmacy.github.io/bxapi/reference/endpoint/sessions#operation-create_session).
  - Import external or higher-level characters with [`POST /v1/characters/import`](https://mmacy.github.io/bxapi/reference/endpoint/characters#operation-import_character) (`kind` set to `"character"`, as written by `Character.to_document`). The server refuses characters that contain stat modifiers or conditions tied to an in-session `effect_id` with 422 `content_invalid`.
  - Export and import full game snapshots (including the master seed) with [`GET /v1/saves/{save_id}/document`](https://mmacy.github.io/bxapi/reference/endpoint/saves#operation-get_save_document) and [`POST /v1/saves/import`](https://mmacy.github.io/bxapi/reference/endpoint/saves#operation-import_save), or export full adventure documents with [`GET /v1/adventures/{adventure_id}/document`](https://mmacy.github.io/bxapi/reference/endpoint/adventures#operation-get_adventure_document).
